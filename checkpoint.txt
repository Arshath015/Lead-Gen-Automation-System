Fixed: gpt-oss-20b forced-tool-call JSON bug, found during live end-to-end verification

Once GROQ_API_KEY was added, live-testing the research-brief generation (nested schema: array of news-item objects, array of source objects) reliably failed with a Groq-side 400 `tool_use_failed` ("Failed to parse tool call arguments as JSON") — gpt-oss-20b was generating well-formed JSON content but failing to correctly string-encode it into the forced tool-call `arguments` field for schemas with nested objects. A single retry did not help (failed identically both times), and it was independently reproduced via a raw fetch script against the Groq API directly (bypassing our code), confirming it's a Groq/model-side quirk, not our schema-consumption bug.

Fix: groqAdapter.ts no longer uses tools/tool_choice at all. It now uses `response_format: {type: "json_schema", json_schema: {name, schema, strict: true}}`, which has the model emit the JSON directly as message content instead of nesting it inside a stringified tool-call argument — sidesteps the encoding bug entirely. Verified with the same nested research-brief schema via an isolated script (200 OK, clean JSON) and then through the real running server. Also added temperature: 0.2 (more deterministic structured output) and kept a defensive one-retry wrapper for the rarer case of the model returning non-JSON content despite strict mode. All object schemas now set additionalProperties: false and list every property (including nullable ones) in required, since Groq's strict json_schema mode requires that subset of JSON Schema.
